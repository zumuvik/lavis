# Module API v1

## Назначение и границы

Module API v1 — статический контракт метаданных встроенных модулей и команд Lavis. Он даёт русскоязычной Help v2 единый источник для списка модулей, карточек команд, примеров, происхождения, уровня риска и возможностей. Реестр компилируется вместе с программой; его можно проверять без Telegram.

Это **не** API динамических плагинов. В v1 нет внешнего загрузчика, установщика, выполнения терминала, `sudo`, `sh`, `bash`, `eval` или произвольных строк команд. `ModuleOrigin::External` — только представимое и валидируемое описание происхождения; оно не загружает код, не разрешает URL, не запускает процесс и не создаёт песочницу.

## Типы метаданных

### Модуль

`ModuleId` — стабильный типовой идентификатор встроенного модуля: `Core`, `System` или `Aliases`.

`ModuleOrigin` описывает происхождение:

- `Builtin` — модуль собран вместе с Lavis;
- `External { author, version, source }` — отображаемые автор, версия и источник внешнего происхождения. Все три строки обязаны быть непустыми, ограниченными по длине, без управляющих и bidi-символов; `source` не может быть локальным абсолютным путём или `file:`-URL.

`ModuleCapability` — заявленная возможность модуля, а не разрешение на обход ограничений:

- `TelegramRpc` — обращение к Telegram RPC;
- `PersistentStateRead` — чтение постоянного локального состояния;
- `PersistentStateWrite` — изменение постоянного локального состояния;
- `HostInformation` — получение информации о хосте;
- `RestrictedProcess` — запуск только заранее определённого ограниченного процесса;
- `Network` — сетевая операция.

`ModuleSpec` содержит `id`, каноническое ASCII-имя `name`, русское `description_ru`, значок `icon`, `origin`, срез `capabilities`, а также флаги `unloadable` и `replaceable`. `unloadable` сообщает, допускает ли контракт выгрузку модуля; `replaceable` — допускает ли замену. В текущем скомпилированном реестре оба флага у всех модулей `false`.

### Команда

`CommandKind` — типовой вид встроенной команды: `Ping`, `Stats`, `Help`, `Fastfetch`, `Alias`, `Prefix` или `Modules`.

`CommandRisk` описывает максимальный характер действия:

- `ReadOnly` — чтение без сохранения изменений;
- `PersistentStateChange` — изменение локального постоянного состояния;
- `RestrictedProcess` — строго ограниченный вызов известной программы;
- `ArbitraryProcess` — произвольный процесс;
- `Privileged` — привилегированное действие.

Последние два значения существуют для полноты модели, но запрещены для встроенных команд Lavis.

`CommandDefinition` связывает `kind` с каноническим `name`, синтаксисом `usage`, русскими `summary_ru` и `description_ru`, списком безпрефиксных `examples`, `risk`, `icon`, флагом `aliasable` и владельцем `module: ModuleId`. `summary_ru` — короткая строка для обзора Help v2; `description_ru` — подробный текст карточки. Каждый пример начинается с имени канонической команды, например `fastfetch --no-profile`, а UI добавляет активный префикс.

## Статические реестры и запросы

Единственные источники метаданных — compile-time статические реестры. Для чтения используйте следующие API:

- `modules()` и `module_by_id(ModuleId)`;
- `module_by_name(&str)`;
- `commands()` и `command_by_kind(CommandKind)`;
- `command_by_name(&str)`;
- `commands_for_module(ModuleId)`;
- `module_for_command(&CommandDefinition)`.

Поиск по имени модуля и команды нечувствителен к ASCII-регистру. Инварианты реестра: идентификаторы и имена уникальны, каждое имя непусто, каждая команда принадлежит зарегистрированному модулю, каждый модуль содержит команду, а совокупность `commands_for_module` покрывает команды ровно по одному разу. Описания, значки и примеры обязательны. Риск `PersistentStateChange` требует `PersistentStateWrite`; `RestrictedProcess` требует `RestrictedProcess`. Встроенным командам запрещены `ArbitraryProcess` и `Privileged`, а встроенным модулям — `Network`.

## Help v2, происхождение и псевдонимы

Help v2 использует `summary_ru`, `description_ru`, `examples`, `commands_for_module` и `ModuleSpec`, а не дублирует каталог команд. Карточка показывает каноническое имя с активным префиксом, русское описание, примеры с тем же префиксом, модуль и происхождение. Происхождение `Builtin` отображается как встроенное; для `External` отображаются только проверенные `author`, `version` и `source`.

Для темы справки действует точный порядок: каноническая команда → существующий псевдоним → модуль → неизвестная тема. Поэтому псевдоним не может затенить команду, но псевдоним с именем модуля остаётся доступен в Help v2. Исполнение команд также резервирует канонические имена; псевдонимы не заменяют их.

## Как зарегистрировать встроенную команду

Регистрация выполняется одним согласованным изменением, в таком порядке:

1. Добавьте `ModuleId` при появлении нового модуля и его `ModuleSpec` в статический реестр.
2. Добавьте `CommandKind` и полный `CommandDefinition`, включая русские поля, безпрефиксные примеры, риск, владельца и возможность псевдонима.
3. Добавьте вариант `Action` для типизированного намерения команды.
4. Добавьте сопоставление `CommandKind` с `Action` в `dispatch`.
5. Добавьте отдельный разбор аргументов в типизированный запрос, если команда принимает аргументы; центральный разборщик уже отделяет префикс и имя команды.
6. Добавьте выполнение `Action` в runtime и проверьте, что transport-детали не протекают в метаданные.
7. Добавьте тесты реестра, разбора, диспетчеризации, Help v2 и поведения runtime.

Не разбирайте префикс повторно в команде. В `examples` пишите `ping`, `help system` или `fastfetch --no-profile`, а не варианты с `,` или другим префиксом.

## Пример: концептуальная команда чтения дисков

Ниже — только документационный пример будущей read-only команды. Он не является инструкцией добавить загрузчик или произвольное выполнение:

```rust
Command::new("df").args(["--output=source,target,size,used,avail,pcent", "-B1"])
```

Команда имела бы `CommandRisk::RestrictedProcess`, а модуль — `ModuleCapability::RestrictedProcess` и `ModuleCapability::HostInformation`. Аргументы фиксированы и типизированы в исходном коде: нет `sh`, `bash`, `eval`, подстановок, пользовательских путей и произвольных строк команд. Процесс получает null stdin, его stdout/stderr захватываются с жёсткой границей размера, выполнение ограничено timeout, а вывод перед отправкой в Telegram санитизируется и ограничивается. Ошибка не должна раскрывать локальные пути, окружение или необработанный stderr.

## Тесты и контроль безопасности

Тестируйте как минимум уникальность и полноту реестров, соответствие риска возможностям, поиск по именам, связь команда↔модуль, порядок разрешения Help v2, безпрефиксность примеров, разбор пустого ввода/не-команды/только префикса/аргументов/повторных пробелов/другого префикса/Unicode и отказ от недопустимых аргументов.

Перед PR выполните:

```bash
nix develop
cargo fmt --check
cargo check --all-targets
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-targets
nix flake check
nix build
```

Проверьте также: команда доступна только исходящему авторизованному аккаунту; секреты, сеанс, API hash, пароли, локальные профили и логи не попадают в Git, ответы и документацию; пути в документации остаются символическими XDG-путями (например, `$XDG_CONFIG_HOME/lavis/fastfetch.json`); процесс, если он разрешён, имеет фиксированную программу и аргументы, null stdin, bounded capture, timeout и санитарную обработку вывода.

## Текущее ограничение

Сегодня production-реестр содержит только скомпилированные встроенные модули. `ModuleOrigin::External` проверяется и может быть безопасно показан в тестовых или будущих метаданных, но не означает поддержку внешнего кода, его загрузку, установку, обновление, изоляцию или песочницу.
